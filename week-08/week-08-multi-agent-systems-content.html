    Multi-Agent Systems with ADK

    Orchestrator-specialist patterns, the sub_agents-vs-AgentTool decision, and ADK's deterministic workflow agents for pipelines and swarms.

    By the end of this lesson, you will be able to

    • Explain why a single agent with too many tools and instructions degrades, and how specialization fixes it.
    • Contrast ADK's two delegation mechanisms: sub_agents (handoff, child owns the conversation) and AgentTool (isolated call, child returns a string).
    • Use ADK's workflow agents (SequentialAgent, ParallelAgent, LoopAgent) to implement a fixed pipeline instead of LLM-driven routing.
    • Build an orchestrator with specialist sub-agents, both ways, in ADK; build the AgentTool-equivalent pattern in LangChain.

    1. Why split one agent into many?

    A single agent with fifteen tools and an instruction paragraph covering five unrelated responsibilities tends to mis-route: it calls the wrong tool, forgets constraints buried on line 12, or blends two tasks into one confused reply. Specialization fixes this the same way it does in human teams: give each agent a narrow job, a short focused instruction, and only the tools it needs. A coordinator then reads the user's intent and delegates.

    This is also a grading concern: your Corte 2 project rubric explicitly rewards "architectural clarity in the systems built" — a coordinator plus two or three well-scoped specialists is far easier to defend live than one agent with an ever-growing instruction string.

    2. Two ways to delegate in ADK

    ADK gives you two distinct mechanisms, and picking the wrong one for the job is the most common multi-agent bug students hit:

    sub_agents (handoff)AgentTool
    Who owns the conversation after delegating?The child agent — control transfersThe parent — child runs in isolation and returns
    What comes back to the parent?Nothing directly; the child replies to the userA string result, which the parent synthesizes into its own reply
    Good for"This whole topic belongs to a different specialist now" (e.g. billing vs. tech support)"I need one focused sub-task's answer to keep working" (e.g. a research lookup)

    sub_agents: LLM-driven handoff

    python
    research_agent = Agent(
    name="research_agent",
    model="gemini-flash-latest",
    description="Looks up facts about the AI Agentic Engineering course schedule.",  # the ONLY thing the router reads
    tools=[get_course_topic],
)

orchestrator = Agent(
    name="orchestrator",
    model="gemini-flash-latest",
    instruction="Delegate schedule questions to research_agent. Handle everything else yourself.",
    sub_agents=[research_agent],   # ADK's AutoFlow routes based on each child's description
)

    The description field is not documentation for humans — it is the coordinator's only signal for when to route to that child. Vague descriptions cause silent mis-routing.

    AgentTool: isolated call-and-return

    python
    from google.adk.tools.agent_tool import AgentTool

research_agent = Agent(name="research_agent", model="gemini-flash-latest", tools=[get_course_topic])

orchestrator = Agent(
    name="orchestrator",
    model="gemini-flash-latest",
    instruction="Use research_agent as a tool whenever you need schedule facts, then keep working.",
    tools=[AgentTool(research_agent)],   # wrapped like any other function tool
)

    Use AgentTool when the parent needs to keep control — e.g. it must combine the specialist's answer with something else before replying.

    3. Workflow agents: fixed pipelines instead of LLM routing

    Sometimes you do not want the LLM deciding the order at all — you want a guaranteed sequence (the syllabus's "pipeline" pattern). ADK ships three workflow agents that orchestrate children deterministically, with no routing LLM call in between:

    • SequentialAgent — runs children in a fixed order, one after another (a pipeline).
    • ParallelAgent — runs children concurrently (a "swarm" that fans out, then you merge results).
    • LoopAgent — re-runs a child until a condition is met or a max-iteration count is hit.
    python
    from google.adk.agents import SequentialAgent

pipeline = SequentialAgent(
    name="research_then_plan_pipeline",
    sub_agents=[research_agent, planner_agent],   # always research_agent first, planner_agent second
)

    Prefer a workflow agent over LLM-driven sub_agents whenever the order is known in advance — it is cheaper (fewer routing calls) and cannot mis-route.

    ⚙️ Tooling corner (3/5): Google Antigravity CLI — scaffolding a specialist agent

    Once your orchestrator exists, growing the team is a repetitive, well-specified task — a good fit for Antigravity:

    terminal
    agy
> In adk/orchestrator_subagents_agent/, add a new sibling agent module "scheduling_agent.py"
  with a root-level scheduling_agent variable (Agent, model="gemini-flash-latest") that has one
  tool for suggesting a study day given a difficulty. Then add it to orchestrator's sub_agents list
  in agent.py and update its instruction to mention when to delegate to it.

    Multi-agent code is where over-trusting generated code is most costly — a wrong description string silently breaks routing without raising an error. Test every new specialist with a prompt that should route to it before moving on.

    Glossary

    Orchestrator / coordinator
    The top-level agent that reads user intent and delegates to specialists.
    sub_agents (handoff)
    ADK delegation where control transfers to the child; the child replies directly to the user.
    AgentTool
    ADK delegation where the child runs in isolation and returns a string the parent must synthesize.
    SequentialAgent / ParallelAgent / LoopAgent
    ADK workflow agents that orchestrate children deterministically, without an LLM routing call.
    Pipeline pattern
    A fixed, ordered sequence of agents (implemented with SequentialAgent).
    Swarm pattern
    Peer agents that can hand off to one another rather than reporting to a single coordinator.

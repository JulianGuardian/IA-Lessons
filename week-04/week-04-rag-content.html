    1. From Semantic Search to RAG

    Last week you built a minimal semantic search function: embed some candidate texts, embed a query, rank by cosine similarity. Retrieval-Augmented Generation (RAG) is that exact idea, formalized into a production pattern with one addition: instead of just returning the best-matching text, you feed it into the model's context so the model can generate an answer grounded in it (Lewis et al., 2020 — see Further Reading).

    RAG solves a problem no amount of prompt engineering can: an LLM only knows what was in its training data (plus whatever you put in the prompt). RAG lets it answer questions about your documents — a course syllabus, a product manual, your own notes — without retraining anything.

    2. RAG Architecture: Four Stages

    StageWhat happensWhen it runs
    IngestionLoad raw source documents (PDFs, markdown, web pages, plain text) into memory.Once per document, or whenever documents change.
    IndexingSplit documents into chunks, embed each chunk, store vectors + text + metadata in a vector store.Once per document, or whenever documents change.
    RetrievalEmbed the incoming user query, search the vector store for the most similar chunks.Every single user query.
    GenerationInsert the retrieved chunks into the prompt alongside the query, ask the LLM to answer using only that context.Every single user query.

    3. Chunking Strategies

    You can't embed an entire 50-page manual as one vector — embedding models have their own input limits, and a single vector for a huge document would be too vague to match specific queries well. So documents are split into chunks first.

    StrategyHow it worksTradeoff
    Fixed-size Split every N characters or tokens, regardless of content structure. Simple and predictable, but can cut a sentence or idea in half.
    Fixed-size with overlap Same as above, but consecutive chunks share a small overlapping window (e.g. last 50 tokens of chunk N = first 50 tokens of chunk N+1). Reduces the "cut mid-idea" problem at the cost of some duplicated content across chunks.
    Structure-aware / recursive Split on natural boundaries first (sections, paragraphs, then sentences) and only fall back to a hard character limit if a section is still too big. Produces more semantically coherent chunks; more implementation effort.
    chunking.py
    def chunk_text(text: str, chunk_size: int = 800, overlap: int = 100) -> list[str]:
    """Fixed-size chunking with overlap, measured in characters."""
    chunks = []
    start = 0
    while start < len(text):
        end = start + chunk_size
        chunks.append(text[start:end])
        start = end - overlap  # step back by `overlap` so chunks share context
    return chunks

sample = open("data/course_notes.txt").read()
chunks = chunk_text(sample, chunk_size=800, overlap=100)
print(f"{len(sample)} chars -> {len(chunks)} chunks")

    Engineering rule of thumb

    Start with fixed-size + overlap (simple, works reasonably well almost everywhere), and measure retrieval quality on real questions before reaching for a fancier structure-aware chunker. Typical starting points: chunks of 500–1000 characters (or 200–400 tokens) with 10–20% overlap.

    4. Vector Stores: ChromaDB and FAISS

    A vector store holds your chunk embeddings and lets you search them efficiently by similarity, instead of the naive "loop over a Python list" approach from last week — essential once you have thousands of chunks instead of six.

    ChromaDBFAISS
    What it isA full embedded vector database: stores text, embeddings, and metadata together, with a simple Python API.A library for fast similarity search over raw vectors (Facebook AI Similarity Search) — you manage the text/metadata yourself.
    PersistenceBuilt-in (PersistentClient) — survives restarts with zero extra code.You serialize the index yourself (faiss.write_index).
    Metadata filteringBuilt-in (filter by any field alongside similarity search).Not built-in; you filter before/after the vector search yourself.
    Best forMost application-level RAG: quick to set up, batteries included. What we'll use today.Very large-scale or latency-critical search where you want fine control over the index type.
    chromadb_indexing.py
    import chromadb

chroma_client = chromadb.PersistentClient(path="./chroma_db")
collection = chroma_client.get_or_create_collection(name="course_notes")

collection.add(
    documents=chunks,
    embeddings=[embed(c) for c in chunks],
    ids=[f"chunk-{i}" for i in range(len(chunks))],
)

results = collection.query(
    query_embeddings=[embed("What is context engineering?")],
    n_results=3,
)
for doc, dist in zip(results["documents"][0], results["distances"][0]):
    print(f"{dist:.3f}  {doc[:80]}...")
    faiss_indexing.py
    import faiss
import numpy as np

vectors = np.array([embed(c) for c in chunks], dtype="float32")
index = faiss.IndexFlatL2(vectors.shape[1])
index.add(vectors)

query_vector = np.array([embed("What is context engineering?")], dtype="float32")
distances, indices = index.search(query_vector, k=3)
for dist, idx in zip(distances[0], indices[0]):
    print(f"{dist:.3f}  {chunks[idx][:80]}...")

    5. Building a Functional RAG System

    The generation step ties everything together: retrieve relevant chunks, then instruct the model to answer using only the retrieved context — the single most important prompting rule in RAG, and the one most responsible for reducing hallucination.

    rag_answer.py
    def answer_with_rag(question: str, n_results: int = 3) -> str:
    results = collection.query(query_embeddings=[embed(question)], n_results=n_results)
    context = "\n\n---\n\n".join(results["documents"][0])

    prompt = f'''Answer the question using ONLY the context below. If the answer isn't
in the context, say you don't have that information — do not make anything up.

Context:
{context}

Question: {question}
Answer:'''

    response = client.models.generate_content(

    Common failure mode

    If your assistant confidently answers questions your documents never mention, check two things first: (1) is the "answer ONLY from context" instruction actually in the prompt, and (2) is retrieval actually returning relevant chunks (print them and read them yourself before blaming the LLM). Most "RAG hallucination" bugs reported by students turn out to be retrieval bugs, not generation bugs.

    7. Key Takeaways & Glossary

    • RAG = retrieval (find relevant chunks) + augmentation (insert them into the prompt) + generation (answer grounded in them).
    • Chunking strategy affects retrieval quality directly — start simple (fixed-size + overlap), tune from there.
    • ChromaDB is the pragmatic default for application-level RAG; FAISS is a lower-level, higher-control alternative for scale.
    • The single highest-leverage prompt instruction in RAG: answer only from the provided context.
    • Most perceived "hallucination" bugs in student RAG systems are actually retrieval bugs — always inspect what was retrieved.
    RAG (Retrieval-Augmented Generation)
    Grounding an LLM's answer in retrieved external documents instead of relying only on its training data.
    Chunk
    A piece of a document, sized to fit a single embedding call and a useful unit of retrieval.
    Vector store
    A database specialized for storing and similarity-searching embeddings (e.g. ChromaDB, FAISS).
    Ingestion / Indexing
    The one-time (or on-update) pipeline that turns raw documents into searchable chunk embeddings.
    Grounding
    Constraining a model's answer to be based on retrieved evidence rather than its own unconstrained generation.

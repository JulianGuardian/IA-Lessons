    LangGraph I: State Graphs, Nodes & Checkpointers

    Trading ADK's implicit, LLM-driven routing for an explicit graph of nodes and edges you can read, test, and persist across calls with a checkpointer.

    By the end of this lesson, you will be able to

    • Explain the difference between ADK's configuration-driven orchestration and LangGraph's explicit graph-as-code model of control flow.
    • Define a StateGraph: a typed state, nodes, fixed edges, and conditional edges.
    • Persist and resume graph state across calls with a checkpointer and a thread_id.
    • Build a small conditional-routing graph and compare it against Week 8's ADK orchestrator.

    1. Implicit orchestration vs. an explicit graph

    In Week 8, an ADK coordinator's control flow was implicit: you wrote an instruction and a list of sub_agents, and an LLM decided the routing at run time. That is flexible, but the control flow itself is not something you can point to in your code — it lives inside the model's reasoning.

    LangGraph takes the opposite approach: you draw the control flow explicitly, as a graph of typed nodes (plain Python functions) connected by edges (fixed, or conditional on the current state). Nothing about which node runs next is hidden inside a prompt — it's a Python function you can unit-test.

    2. StateGraph basics

    Every LangGraph app starts with a typed state — the single object every node reads from and writes to:

    python
    from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class PlannerState(TypedDict):
    question: str
    route: str
    result: str

def classify_node(state: PlannerState) -> dict:
    # a real node would call an LLM here; kept deterministic for the demo
    q = state["question"].lower()
    if "week" in q and "hour" in q:
        route = "both_node"
    elif "hour" in q:
        route = "planner_node"
    else:
        route = "research_node"
    return {"route": route}

def route_after_classify(state: PlannerState) -> str:
    return state["route"]  # must return a node name (or END) that was registered with add_node

builder = StateGraph(PlannerState)
builder.add_node("classify", classify_node)
# ... add research_node, planner_node, both_node, respond_node here (see the walkthrough) ...
builder.add_edge(START, "classify")
builder.add_conditional_edges("classify", route_after_classify)
graph = builder.compile()

    Each node returns only the keys it wants to update — LangGraph merges that partial dict into the shared state. add_conditional_edges takes a plain function that inspects state and returns the name of the next node (or END).

    3. Checkpointers: the real answer to Week 7's "how does state persist?"

    In Week 7 you saw ADK's built-in session.state with user:/ app:/temp: scopes. LangGraph's equivalent is a checkpointer: it snapshots the full state after every node runs, keyed by a thread_id you choose. Pass the same thread_id again and the graph resumes exactly where it left off — across separate invoke() calls, even separate process runs if you use a persistent checkpointer instead of the in-memory one.

    python
    from langgraph.checkpoint.memory import InMemorySaver

checkpointer = InMemorySaver()
graph = builder.compile(checkpointer=checkpointer)

config = {"configurable": {"thread_id": "student-42"}}
graph.invoke({"question": "What does week 9 cover?"}, config=config)
graph.invoke({"question": "And how many hours if it's hard?"}, config=config)  # same thread: history persists

print(graph.get_state(config).values)  # inspect exactly what is currently checkpointed

    InMemorySaver is for development — it disappears when the process exits. Swapping in a durable one (e.g. a Postgres-backed saver) for production is a config change, not a rewrite, exactly like swapping ADK's SessionService.

    4. Walkthrough: the full routing graph

    The complete graph — three worker nodes feeding into one response node:

    python
    def research_node(state: PlannerState) -> dict:
    return {"result": f"Week topic lookup for: {state['question']}"}

def planner_node(state: PlannerState) -> dict:
    return {"result": f"Study-hour estimate for: {state['question']}"}

def both_node(state: PlannerState) -> dict:
    return {"result": f"Topic + hours for: {state['question']}"}

def respond_node(state: PlannerState) -> dict:
    return {"result": f"Final answer -> {state['result']}"}

builder = StateGraph(PlannerState)
for name, fn in [("classify", classify_node), ("research_node", research_node),
                  ("planner_node", planner_node), ("both_node", both_node),
                  ("respond", respond_node)]:
    builder.add_node(name, fn)

builder.add_edge(START, "classify")
builder.add_conditional_edges("classify", route_after_classify)  # -> research_node | planner_node | both_node
for worker in ["research_node", "planner_node", "both_node"]:
    builder.add_edge(worker, "respond")
builder.add_edge("respond", END)

graph = builder.compile(checkpointer=InMemorySaver())

    Run the full, LLM-backed version of this graph in agents/week-09-langgraph-i/langgraph/app.py.

    ⚙️ Tooling corner (4/5): Google Antigravity CLI — scaffolding a new graph node

    terminal
    agy
> In app.py, add a new node "summarize_node" that takes PlannerState and returns a one-line
  summary of state["result"] using the LLM already defined as `llm` in this file. Wire it in
  between "respond" and END, updating the add_edge calls accordingly. Do not change existing nodes.

    Graphs fail silently if you forget to rewire an edge (the new node just never runs) — always call graph.invoke(...) with a test input immediately after any generated edge change.

    Glossary

    StateGraph
    LangGraph's core class: a typed state plus nodes and edges, compiled into a runnable graph.
    Node
    A plain Python function that reads the current state and returns a partial update.
    Conditional edge
    An edge whose destination is decided at run time by a routing function inspecting state.
    Checkpointer
    Persists graph state after every node run, keyed by thread_id, enabling resume across calls.
    thread_id
    The key a checkpointer uses to identify one persisted conversation/run.

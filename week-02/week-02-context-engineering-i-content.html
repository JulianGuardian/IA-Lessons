    Context Engineering I

    System prompts, few-shot examples, chain-of-thought reasoning, and forcing reliable JSON output from an LLM.

    Learning objectives

    • Explain the shift from "prompt engineering" to "context engineering" and why it matters for engineered systems, not just chat.
    • Write an effective system prompt that separates role/behavior instructions from the user's actual request.
    • Use few-shot examples to steer output format and style without fine-tuning.
    • Apply chain-of-thought prompting to improve multi-step reasoning, and recognize when it's unnecessary overhead.
    • Force an LLM to return valid, schema-conformant JSON using Gemini's structured output mode.

    1. From Prompt Engineering to Context Engineering

    Last week we treated the prompt as a single string. In real systems, what you send to the model is rarely just "the user's question" — it's a carefully assembled package: instructions about how to behave, examples of the desired output, retrieved facts, conversation history, and finally the user's request. Context engineering is the discipline of designing and managing everything inside that context window, deliberately, as a first-class engineering artifact — not something you improvise in a text box.

    Today we build the first two layers — system prompts and few-shot examples — plus two techniques that change how the model reasons and responds: chain-of-thought and structured JSON output. Retrieved context and long conversation history are Weeks 3–4.

    2. System Prompts

    A system prompt (or system instruction) sets persistent behavior for the whole conversation: role, tone, constraints, output format, things to refuse. It is passed separately from the user message so the model can weight it differently and so your application code never has to re-state the same rules on every turn.

    2.1 What belongs in a system prompt

    • Role and persona: "You are a customer support assistant for a bike rental company."
    • Scope and refusals: "Only answer questions about bike rentals; if asked anything else, say you can't help with that."
    • Style and format rules: "Keep answers under 3 sentences. Never use emoji."
    • Tool/behavior instructions (more relevant from Week 6 onward, once agents have tools).

    2.2 What doesn't belong there

    Anything that changes per request — the actual question, retrieved documents, this turn's data — belongs in the user message or a separate context block, not baked into the system prompt. Mixing the two makes your system prompt balloon and your application harder to reason about and test.

    system_instruction example
    response = client.models.generate_content(
    model=MODEL,
    contents="My bike's front brake feels loose, what should I check?",
    config=types.GenerateContentConfig(
        system_instruction=(
            "You are a support assistant for a bike rental company. "
            "Only answer questions related to bike rentals, maintenance, and safety. "
            "Keep answers under 3 sentences. If asked something unrelated, politely decline."
        ),
    ),
)
print(response.text)

    Engineering rule of thumb

    Treat your system prompt like source code: version it, keep it in a file (not a hardcoded string scattered across the codebase), and change one instruction at a time so you can tell what broke or improved.

    3. Few-Shot Prompting

    Zero-shot prompting asks the model to do a task with instructions alone. Few-shot prompting adds a handful of worked examples (input → desired output pairs) directly in the prompt. The model doesn't "learn" in the training sense — it's pattern-matching the shape of your examples for this single call, a mechanism often called in-context learning.

    Few-shot is most useful when:

    • The desired output format is unusual or specific (a particular label taxonomy, a terse style, a non-obvious structure).
    • Instructions alone are ambiguous, but "show, don't tell" resolves the ambiguity in one example.
    • You need consistency across many similar calls (e.g. classifying support tickets the same way every time).
    few-shot sentiment classifier
    prompt = '''Classify the sentiment of a review as positive, negative, or neutral.

Review: "Fast shipping and the product works great."
Sentiment: positive

Review: "It arrived broken and support never replied."
Sentiment: negative

Review: "It's fine, does what it says on the box."
Sentiment: neutral

Review: "Absolutely love it, exceeded expectations!"
Sentiment:'''

response = client.models.generate_content(model=MODEL, contents=prompt)
print(response.text.strip())  # -> positive

    Keep example counts small (2–5 is typical) and representative of the edge cases you actually care about — more examples cost more tokens without necessarily improving quality, and can even bias the model toward whatever pattern happens to repeat in your examples (e.g. always picking the last label shown).

    4. Chain-of-Thought Prompting

    Chain-of-thought (CoT) prompting asks the model to work through intermediate reasoning steps before giving a final answer, instead of jumping straight to a conclusion (Yao et al., 2022, and the broader CoT literature it builds on — see Further Reading). For multi-step arithmetic, logic, or planning tasks, this measurably improves accuracy, because it gives the model "room" to build up an answer token by token instead of having to get it right in one shot.

    chain-of-thought example
    prompt = '''A store had 120 apples. It sold 35% of them in the morning and 28 more in the afternoon.
How many apples are left? Think step by step, then give the final answer on its own line
starting with "Answer:".'''

response = client.models.generate_content(
    model=MODEL, contents=prompt,
    config=types.GenerateContentConfig(temperature=0.1),
)
print(response.text)

    When CoT is not worth it

    For simple lookups, classification, or extraction, forcing step-by-step reasoning just adds latency and token cost without improving quality — and makes the output harder to parse programmatically. It's also largely redundant on models with built-in "thinking"/reasoning modes, which already reason internally before answering. Reach for explicit CoT when a task genuinely has multiple dependent steps.

    5. Structuring Output: JSON Mode & Schema Forcing

    The moment an LLM's output feeds into code rather than a human, you need it to come back in a predictable shape. Asking nicely ("please respond in JSON") is not reliable enough for production — models add prose before/after the JSON, use trailing commas, or rename fields. The fix is structured output: you give the API a schema, and the model is constrained to only produce output matching it.

    schema-forced JSON output
    from pydantic import BaseModel

class TicketTriage(BaseModel):
    category: str        # "billing" | "technical" | "account" | "other"
    urgency: str          # "low" | "medium" | "high"
    summary: str

response = client.models.generate_content(
    model=MODEL,
    contents="My card was charged twice for the same order and I need this fixed today.",
    config=types.GenerateContentConfig(
        response_mime_type="application/json",
        response_schema=TicketTriage,
    ),
)

import json
data = json.loads(response.text)
print(data)
# or, even more convenient:
ticket: TicketTriage = response.parsed
print(ticket.category, ticket.urgency)

    Two settings work together here: response_mime_type="application/json" tells the API you want JSON back, and response_schema (a Pydantic model, dataclass, or explicit JSON-schema dict) constrains which JSON. The SDK will even parse it back into a typed object for you via response.parsed. This single feature is what makes reliable function calling, tool use, and agent planning possible — we'll lean on it heavily from Week 6 onward.

    Engineering rule of thumb

    Combine schema forcing with low temperature. Structure controls the shape; temperature still controls the wording inside string fields, and low variance there makes downstream parsing and testing far more reliable.

    7. Key Takeaways & Glossary

    • Context engineering generalizes prompt engineering to everything in the context window: system prompt, examples, retrieved data, history, and the request.
    • A system prompt holds persistent behavior; the user message holds what changes per call.
    • Few-shot examples are the fastest way to fix output format/style without fine-tuning.
    • Chain-of-thought helps on genuinely multi-step reasoning tasks; it's overhead on simple ones.
    • Schema-forced JSON output turns unreliable free text into a typed, parseable contract your code can depend on.
    System prompt
    Persistent instructions defining role, tone, and constraints, sent separately from the user message.
    Zero-shot / Few-shot
    Prompting with instructions alone vs. with worked input→output examples included.
    In-context learning
    The model adapting its behavior to patterns shown within a single prompt, without weight updates.
    Chain-of-thought (CoT)
    Prompting the model to produce intermediate reasoning steps before a final answer.
    Structured output / schema forcing
    Constraining a model's response to conform to a given JSON schema.

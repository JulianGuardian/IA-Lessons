    Google ADK: Architecture, Tools, State & Sessions

    What Runner, SessionService, and events actually do under adk web's chat UI — plus the four state scopes and building an agent from an empty folder, step by step.

    By the end of this lesson, you will be able to

    • Describe ADK's core building blocks: Agent, Runner, SessionService, and the event stream that connects them.
    • Write custom function tools, including tools that read and write session state via ToolContext.
    • Explain ADK's four state scopes — session, user:, app:, temp: — and pick the right one for a given piece of data.
    • Build, run, and inspect an ADK agent from an empty folder, end to end.

    1. ADK architecture: the four pieces

    Last week you ran an ADK agent without looking under the hood. Four objects do all the work:

    • Agent (google.adk.agents.Agent, an alias for LlmAgent) — declares the model, the system instruction, and the tools available. This is the object you defined as root_agent last week.
    • Runner — executes one user turn: calls the model, executes any requested tools, feeds results back, repeats (the PRA loop from Week 6), and streams out events as it goes.
    • SessionService — owns session.state, the dictionary an agent's tools read and write. adk web uses an in-memory one; production deployments (Week 14) swap in a database-backed one without changing any agent code.
    • Events — every model response, tool call, and tool result is an event. The adk web trace panel you used last week is just a viewer over this event stream.

    Explicitly, without the CLI wrapper:

    python
    import asyncio
from google.adk.agents import Agent
from google.adk.runners import InMemoryRunner
from google.genai import types

root_agent = Agent(model="gemini-flash-latest", name="demo_agent", instruction="Be concise.")

async def main():
    runner = InMemoryRunner(agent=root_agent, app_name="demo_app")
    session = await runner.session_service.create_session(app_name="demo_app", user_id="student_1")
    content = types.Content(role="user", parts=[types.Part(text="Hello!")])
    async for event in runner.run_async(user_id="student_1", session_id=session.id, new_message=content):
        if event.is_final_response():
            print(event.content.parts[0].text)

asyncio.run(main())

    This is exactly what adk web does for you, with a chat UI and trace viewer wrapped around it.

    2. Custom tools, formally

    You wrote plain-function tools in Week 6. ADK turns any typed Python function with a docstring into a tool automatically — the function's name, parameter types, and docstring become the schema the model sees. Two rules matter in practice:

    • Type hints are not optional. ADK derives the JSON schema from them; an untyped parameter cannot be turned into a reliable tool schema.
    • Return a dict, not a string. Structured results are easier for the model to reference precisely, and easier for your own code to test.

    To read or write state from inside a tool, add a tool_context: ToolContext parameter — ADK injects it automatically; you never pass it yourself when calling the tool from a prompt:

    python
    from google.adk.tools.tool_context import ToolContext

def log_study_session(topic: str, hours: float, tool_context: ToolContext) -> dict:
    """Record a completed study session for the current user."""
    log = tool_context.state.get("session_log", [])
    log.append({"topic": topic, "hours": hours})
    tool_context.state["session_log"] = log
    return {"logged": True, "total_sessions": len(log)}

    3. State scopes: session, user, app, temp

    tool_context.state is a single dictionary, but the key prefix tells ADK how far a value should travel:

    PrefixScopeUse for
    (none)Current session only — gone on a new sessionConversation-specific facts (Week 3's sliding window/summary)
    user:Shared across every session for this user_idPreferences that should persist across conversations
    app:Shared across every session, every user, in this appApp-wide config or shared counters
    temp:Current invocation only — never persistedScratch values a tool needs only within one turn
    python
    def set_preferred_pace(pace: str, tool_context: ToolContext) -> dict:
    """Remember the user's preferred study pace ('relaxed', 'normal', or 'intense') across sessions."""
    tool_context.state["user:preferred_pace"] = pace   # survives into every future session for this user_id
    return {"preferred_pace": pace}

    Pick the narrowest scope that does the job — state that does not need to outlive the session should not use user:, since it will otherwise leak into unrelated future conversations.

    4. Walkthrough: building an agent from an empty folder

    Formalizing what adk web did automatically last week — the exact steps, every time:

    bash
    mkdir -p my_agent && cd my_agent
touch __init__.py agent.py .env
echo "from . import agent" > __init__.py
echo 'GOOGLE_API_KEY=your-key-here' > .env
# write root_agent = Agent(...) inside agent.py
cd ..
adk web .   # discovers every subfolder with __init__.py + agent.py, launches a chat UI for each

    The three files are non-negotiable: __init__.py makes the folder importable and signals ADK to look inside it; agent.py must define a module-level root_agent; .env supplies credentials. Everything else (extra modules, tests, a README) is up to you.

    Glossary

    Runner
    The ADK object that executes one user turn: drives the model/tool loop and streams events.
    SessionService
    Owns session.state; swappable between in-memory and persistent backends without changing agent code.
    Event
    A single step in a run — a model response, a tool call, or a tool result — streamed by the Runner.
    ToolContext
    Object ADK injects into a tool function to expose state and other run-time context.
    State scope prefix
    user:, app:, or temp: on a state key, controlling how far a value persists.

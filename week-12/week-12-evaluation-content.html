    1. Why "it worked when I tried it" doesn't scale

    LLM outputs are non-deterministic, and a prompt or tool change that improves one case can silently break another. Without a repeatable evaluation suite, every change to your Corte 2/3 project is a gamble you can only check by re-testing every prompt you remember by hand — which does not scale past a handful of cases, and catches nothing you forgot to try.

    Three levels of evaluation

    LevelChecksExample
    UnitOne function/tool in isolation, no LLM callassert estimate_study_hours("x", "hard")["hours"] == 7
    IntegrationDid the agent call the right tools, in the right order?ADK's trajectory evaluator (Section 4)
    End-to-endIs the final answer correct/acceptable to a user?ADK's response-match evaluator; LLM-as-judge (Section 3)

    Run unit tests on every commit (cheap, deterministic); run integration and e2e evals before anything you'd call "done" — including before your Corte 3 delivery.

    2. Quality metrics for RAG and agent answers

    Faithfulness
    Is every claim in the answer actually supported by the retrieved context? An answer can be fluent and still unfaithful if it adds unsupported details.
    Relevance
    Does the answer actually address what the user asked, even if every sentence in it is individually true?
    Hallucination
    A specific failure of faithfulness: a confident claim with no support in the context or tool results at all.

    None of these three has a purely mechanical test — "is this sentence supported by that paragraph" is itself a language-understanding task. That is exactly the gap LLM-as-judge (next section) fills.

    3. LLM-as-judge

    Use a second LLM call to score the first one's output against a rubric, with Week 2's schema-forcing so the score is machine-readable, not prose you have to re-parse by hand:

    python
    from pydantic import BaseModel, Field
from langchain_google_genai import ChatGoogleGenerativeAI

class JudgeScore(BaseModel):
    faithfulness: int = Field(ge=1, le=5, description="1=unsupported claims, 5=fully grounded in context")
    relevance: int = Field(ge=1, le=5, description="1=off-topic, 5=directly answers the question")
    rationale: str

judge_llm = ChatGoogleGenerativeAI(model="gemini-flash-latest").with_structured_output(JudgeScore)

def judge(question: str, context: str, answer: str) -> JudgeScore:
    return judge_llm.invoke(
        f"Question: {question}\nContext: {context}\nAnswer: {answer}\n\n"
        "Score the answer's faithfulness to the context and relevance to the question, 1-5 each, "
        "and give a one-sentence rationale."
    )

    Judge bias is real: LLM judges tend to prefer longer, more confident-sounding answers regardless of correctness, and score their own model family's outputs more favorably. Treat judge scores as a fast, imperfect signal for regressions across a whole dataset — not as ground truth for any one answer. Spot-check a sample by hand before trusting a judge-based number in your project write-up.

    4. ADK's evaluation framework

    ADK ships a purpose-built eval format: an .evalset.json file records real conversations — the user's message, the expected tool calls (trajectory), and the expected final response — and two evaluators score a fresh run against it:

    • tool_trajectory_avg_score — exact match of the tool-call sequence against what you recorded. Deterministic, fast, good for CI. Defaults to requiring a perfect match (1.0).
    • response_match_score — ROUGE-1 similarity between the final response and your recorded reference. Allows wording differences; defaults to 0.8.
    json
    {
  "eval_set_id": "campus_helper_eval_v1",
  "eval_cases": [{
    "eval_id": "topic_lookup_week_7",
    "conversation": [{
      "invocation_id": "inv-1",
      "user_content": {"parts": [{"text": "What topic does week 7 cover?"}], "role": "user"},
      "final_response": {"parts": [{"text": "Week 7 covers Google ADK."}], "role": "model"},
      "intermediate_data": {
        "tool_uses": [{"name": "get_course_topic", "args": {"week": 7}}],
        "intermediate_responses": []
      }
    }],
    "session_input": {"app_name": "campus_helper_agent", "user_id": "test_user", "state": {}}
  }]
}

    Run it from the CLI, or programmatically in a pytest suite (useful for CI):

    terminal + pytest
    # CLI
adk eval campus_helper_agent evalsets/campus_helper.evalset.json --config_file_path=evalsets/test_config.json

# Programmatic (pytest)
import pytest
from google.adk.evaluation.agent_evaluator import AgentEvaluator

@pytest.mark.asyncio
async def test_campus_helper_agent():
    await AgentEvaluator.evaluate(
        agent_module="campus_helper_agent",
        eval_dataset_file_path_or_dir="evalsets/campus_helper.evalset.json",
    )

    ⚙️ Tooling corner (1/4): Google Antigravity CLI — drafting eval cases

    Writing evalset JSON by hand is tedious and error-prone. Describe the scenarios in plain language and let Antigravity draft the structure — then verify every field yourself:

    terminal
    agy
> Add two more eval_cases to evalsets/campus_helper.evalset.json: one where the user asks for study
  hours on an "easy" topic (expects estimate_study_hours), and one ambiguous question with no week
  number that should NOT call any tool. Follow the existing JSON schema exactly.

    Eval data is the closest thing you have to ground truth for your project — a wrong expected value here makes every future evaluation run lie to you. Read every generated case before trusting it.

    Glossary

    Trajectory
    The sequence of tool calls (name + arguments) an agent produced for one input.
    tool_trajectory_avg_score
    ADK's evaluator comparing an actual trajectory to an expected one.
    response_match_score
    ADK's ROUGE-1-based evaluator comparing a final response to a reference.
    LLM-as-judge
    Using a second LLM call, with a fixed rubric and structured output, to score a first LLM's output.
    Judge bias
    A judge LLM's tendency to favor longer or more confident answers regardless of correctness.
